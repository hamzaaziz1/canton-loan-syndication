# Identity and trust

How the nodes and parties on this network establish who they are, which keys exist and where, and what each signed statement in the topology means. Everything here can be reproduced on the running network:

```bash
make console SCRIPT=identity-report   # each node's id and public keys
make console SCRIPT=trust-chain       # the synchronizer's topology state, by mapping type
make console SCRIPT=governance-check  # onboarding rules and participant permissions
```

## Two separate trust systems

| Layer | Keys | Protects | On this network |
|---|---|---|---|
| Canton protocol | namespace, signing and encryption keys, published as topology transactions | what is said: views are encrypted to their recipients and every message is signed | every node |
| Transport | X.509 certificates from the network's dev CA | the channel: who you are talking to, and connection metadata | mutual TLS on admin APIs, TLS on ledger APIs, plaintext on the sequencer public API ([ADR 0002](adr/0002-sequencer-public-api-transport.md)) |

The two are independent. A plaintext connection to the sequencer still carries only encrypted, signed protocol messages, and a valid TLS certificate does not authorise anything on the ledger.

## Identities

Every node and party is named `name::fingerprint`, where the fingerprint is the hash of a namespace root key. Nodes carry a role prefix:

```
SEQ::sequencer1::122074e9d3c1...   synchronizer sequencer
MED::mediator1::1220d5abc49a...    synchronizer mediator
PAR::agent::1220b3130bb6...        participant
AgentBank::1220b3130bb6...         party, no prefix
```

A party created by a participant takes that participant's namespace by default. That is why `AgentBank` and `Borrower` share the agent node's fingerprint.

## Keys each node holds

| Key | Algorithm | Used for |
|---|---|---|
| namespace | Ed25519 | signing topology transactions, the identity root |
| signing | Ed25519 | protocol messages: confirmations and verdicts |
| sequencer-auth | Ed25519 | authenticating to the sequencer |
| encryption | EC P-256 | receiving encrypted transaction views (participants only) |

The sequencer and mediator have no encryption key. They cannot decrypt a transaction view, whoever operates them, which is the structural reason the synchronizer columns in the [privacy proof](privacy-proof.md) are empty.

## The trust chain

The synchronizer's topology state after the borrower node joined:

| Mapping | Count | What it is | Signed by |
|---|---|---|---|
| NamespaceDelegation | 8 | root certificates, plus the borrower's intermediate delegation and the retired borrower identity's root certificate | each namespace's own root key |
| OwnerToKeyMapping | 7 | each node binding its operational keys | the node's namespace key and each key itself (proof of possession) |
| DecentralizedNamespaceDefinition | 1 | the synchronizer's namespace `1220561e...`, defined as owners plus a threshold | the owners |
| SequencerSynchronizerState, MediatorSynchronizerState | 1 each | which sequencers and mediators serve `loansync` | the synchronizer namespace |
| SynchronizerParametersState | 1 | dynamic rules, including `onboarding restriction = RestrictedOpen` | the synchronizer namespace |
| SynchronizerTrustCertificate | 5 | each participant's own request to join, including the retired identity's | the participant |
| ParticipantSynchronizerPermission | 4 | the owners admitting each current participant | the synchronizer namespace |
| PartyToParticipant | 5 | which node hosts each party, with which permission | the party's namespace and the hosting node |
| VettedPackages | 5 | the Daml packages each participant agrees to run | the participant |

Package vetting has no EVM equivalent. A participant refuses to process a transaction that uses code it has not vetted, so a counterparty cannot push new contract logic onto another organisation's node.

## Who governs the synchronizer

`DecentralizedNamespaceDefinition(namespace = 1220561e..., threshold = 1, owners = 122074e9...)`. The synchronizer is owned by a set of one: sequencer1's root key, which was generated by the node and is stored in the sequencer's database. Anyone with that database can change who serves the synchronizer, its parameters and who may join.

A production synchronizer would have several owners from different organisations and a threshold above one, so that no single operator can change the rules alone.

## Party custody

| Party | Namespace | Hosting decided by | Transactions signed by |
|---|---|---|---|
| `Borrower::1220b313...` | the agent node's | the agent node's root key | the agent node |
| `BorrowerCo::1220002df084...` | the borrower node's, rooted in an offline key | the offline root, through a revocable delegation | the borrower node |
| external party (not used here) | the party's own | the party's key | the party's key, per transaction, through interactive submission |

`PartyToParticipant(Borrower -> agent)` carries a single signature from `1220b313...`, because the party's namespace and its hosting node are the same. The borrower cannot move this party to its own node without the agent signing. `BorrowerCo`'s hosting is signed by the borrower node's intermediate key `12200bda...`, which is valid only because the offline root delegated to it.

## Offline root namespace key

The borrower participant was started with `init.identity.type = manual` and given its identity in an offline ceremony (`scripts/offline-root-ceremony.sh`, built on Canton's `scripts/offline-root-key` tooling):

1. The waiting node generated an intermediate key with usage `NamespaceOnly` and exported its public half.
2. At the offline site, a directory outside the repository that is never mounted into a container, OpenSSL created an Ed25519 root key.
3. The root signed a delegation to itself, the namespace's trust anchor.
4. Before anything was signed for the node, the SHA-256 of the transferred public key was compared with the hash the node printed. They matched (`b5493698...`).
5. The root signed a delegation to the intermediate key, allowed to sign everything except further namespace delegations (`not-nsd`).
6. The two certificates were imported with `topology.init_id`, and the node took the identity `PAR::borrower::1220002df084...`.

The node holds the intermediate key, its operational keys and its encryption key. It does not hold `1220002df084...`. A full compromise of the borrower node yields the intermediate key, which the offline root can revoke and replace, and the identity survives. A root namespace key cannot be rotated: retiring one means a new namespace, new parties and moving contracts.

## Key management today, and what production would change

| Today | Production |
|---|---|
| Root namespace keys for the synchronizer, agent, lendera and lenderb were generated by the nodes and live in their databases | offline roots, as for the borrower, or a KMS with the root administratively isolated |
| Node private keys are stored unencrypted in Postgres, so a database dump contains them | KMS-backed keys or envelope encryption |
| One dev CA on the developer's laptop, 825-day leaf certificates | the organisation's PKI, short-lived certificates, automated rotation |
| The synchronizer has a single owner | several owners from different organisations, threshold above one |
| The offline site is a directory on the same laptop | a separate, ideally air-gapped machine, or an HSM |

## Transport security

- Every admin API requires a client certificate. Without one, the TLS 1.3 handshake completes and the first request fails with `tlsv13 alert certificate required`.
- Each node's own bootstrap uses the node's certificate as its admin client certificate, so node certificates allow both server and client use.
- Node certificates list `IP:0.0.0.0` as a subject alternative name. Nodes bind their APIs on `0.0.0.0`, and a node's in-process console connects to that address and checks it against the certificate.
- Each container mounts only its own private key, owned by the container's user (uid 1001) with mode 600. The CA key is never mounted.
- The sequencer public API stays on plaintext, for the reasons in [ADR 0002](adr/0002-sequencer-public-api-transport.md).

## Operating lessons

- Console commands take and return admin API client types. Import data types from `com.digitalasset.canton.admin.api.client.data`, not from the node's internal packages. The class names are identical, and a type mismatch is the only hint.
- Canton compiles a whole console script before running any of it. Wrapping the mutating calls in `if (false)` gives a dry run that checks every call and type without touching the network.
- Retire an identity before destroying its keys. The borrower node's first identity was wiped along with its database, so its self-signed statements stay in the topology permanently. Revoking its permission is what made it harmless.
