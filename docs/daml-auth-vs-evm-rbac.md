# Daml authorisation compared with EVM access control

Written for Solidity developers. Every Daml example is from this repo.

## Summary

| Question | EVM | Daml |
|---|---|---|
| Who can trigger a state change | `require(msg.sender == x)`, `onlyRole` | `controller` on a choice |
| Who must agree for state to exist | nothing built in, you verify signatures yourself | `signatory`, enforced by the ledger |
| Who can read state | everyone | stakeholders (signatories and observers) and informees of actions |
| Delegation | `approve`, role grants, stored EIP-712 signatures | a contract the delegator already signed |
| Replay protection | nonces | consuming choices archive their input |
| Reentrancy | guard modifiers | no callbacks into the caller; races become contention instead |
| Superuser | `owner`, `DEFAULT_ADMIN_ROLE` | none at contract level |

## 1. Authority is part of the data

In Solidity, access control is code you write around storage. In Daml, it is part of what a contract is. A `Mandate` lists two signatories:

```haskell
template Mandate
  with
    borrower : Party
    agent    : Party
    terms    : FacilityTerms
  where
    signatory borrower, agent
```

No transaction can create a `Mandate` unless both parties authorised it. The agent cannot forge one, even on its own node, and `test_mandate_authorisation` checks exactly that. There is no check to forget, because the ledger refuses the create before any of our code runs.

The nearest Solidity version:

```solidity
struct Mandate { address borrower; address agent; uint256 total; bool accepted; }
mapping(bytes32 => Mandate) public mandates;

function request(bytes32 id, address agent, uint256 total) external {
    require(mandates[id].borrower == address(0), "exists");
    mandates[id] = Mandate(msg.sender, agent, total, false);
}

function accept(bytes32 id) external {
    Mandate storage m = mandates[id];
    require(msg.sender == m.agent, "not agent");
    require(!m.accepted, "already accepted");
    m.accepted = true;
}
```

Both `require` lines that guard state are things a developer can get wrong. In Daml the first is impossible because contract ids are generated by the ledger, and the second is structural because `Accept` is a consuming choice: once it runs, the request no longer exists.

## 2. A controller brings authority, not just permission

`controller agent` reads like `require(msg.sender == agent)`, but it does more. Inside a choice the body acts with the authority of the contract's signatories plus the controller. That is how `MandateRequest.Accept` can create a `Mandate` signed by both parties: the borrower's authority comes from the request it signed, and the agent's comes from exercising.

The clearest case is `Commitment.Allocate`. The `Commitment` is signed by the agent and the lender, so when the agent exercises `Allocate` during `SyndicateBook.Close`, the new `Participation` carries the lender's signature without the lender taking part in the close.

The Solidity equivalent would store an EIP-712 signature from each lender over the commitment terms, then verify it at close time, with a nonce and a deadline to stop replay. In Daml the signed `Commitment` contract is that stored signature, and the ledger does the verification.

## 3. Propose and accept instead of approve and transferFrom

Multi-party agreement in Daml is built from one pattern: one party creates a proposal it signs, the counterparty exercises a choice on it, and the result is signed by both. This repo uses it twice:

- `MandateRequest` signed by the borrower, accepted by the agent, becomes `Mandate`
- `LenderInvitation` signed by the agent, committed by the lender, becomes `Commitment`

`approve` and `transferFrom` are a weaker version of the same idea. The allowance is a standing permission, not a specific agreement, which is why unlimited approvals are a recurring source of losses.

## 4. Visibility is designed, not given

On EVM every node stores every contract, and privacy has to be added from outside. In Daml a contract is sent only to the nodes hosting its stakeholders. Two rules shape this repo:

1. Signatories and observers see a contract created and archived.
2. An informee of an exercise sees the whole subtree under it, including the choice arguments and every contract created inside.

Rule 2 is easy to break by accident. If `Close` were a choice on `Mandate`, the borrower would be an informee and would see every lender's allocation. So `Close` lives on `SyndicateBook`, which only the agent signs, and the borrower sees only the `Mandate.Execute` subtree, which carries the total and nothing else. The full table is in [design/stakeholder-matrix.md](design/stakeholder-matrix.md).

The same thinking applies to submissions. When the agent approves a drawdown, it submits `Approve` and one `CallFunds` per lender as separate roots in one transaction. Each root has its own informees, so the borrower never sees the pro rata split.

## 5. Things with no direct equivalent

**No contract-level superuser.** There is no `owner` that can override signatories. The trust question moves to the infrastructure: whoever operates the participant node that hosts a party can submit commands as that party, much like a custodial wallet. Canton supports external parties that hold their own signing keys, which removes that trust. The identity doc covers how hosting is established.

**No global iteration.** A party can only query contracts it is a stakeholder of, so there is no "loop over all facilities". Off-ledger read models, such as the Postgres projector in this repo, fill that gap per party.

**Contention instead of reentrancy.** A choice cannot be called back by an external contract mid-execution, so reentrancy bugs do not exist. The trade-off is that two transactions consuming the same contract race, and one fails. `FacilityAgreement` is archived and recreated on every drawdown, so concurrent approvals against the same facility must be retried by the client.

## 6. Trust assumptions in this design

- The agent is trusted to pair `Acknowledge` with `Distribute` correctly. Nothing on the ledger forces the two together. The multi-root submission makes them atomic but does not bind them. A stricter design would route both through one agent-only contract holding the participation ids.
- The borrower is hosted on the agent's participant, so its privacy from the agent's operator is contractual, not technical.
- Pro rata shares are rounded to 10 decimal places. The residual policy, usually assigning dust to the lead arranger, is documented but not implemented.
